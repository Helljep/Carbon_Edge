# CarbonEdge

A prototype dashboard for **early detection of machine faults and energy waste in industrial plants**. It streams machine sensor data through an anomaly-detection model and shows live health, alerts and ESG-style reports.

> **Status: prototype.** One part runs on **real recorded data** (bearing vibration, below). The rest of the dashboard (kiln KPIs, plant heatmap, reports) still uses **simulated data**. Nothing here has been validated on a live plant.

---

## What is real, and what is simulated

The **Dashboard** page is now driven entirely by replayed real data. One shared feed streams three recorded datasets from the backend, and the KPIs, main chart, machine explorer, status map and live-status panel all read from it.

**How alerts work.** They are produced by simple rules, not by a separate model, and they only fire on replayed data:
* Bearing: High alarm after 3 anomaly snapshots in a row; High escalation if the score exceeds 10x the threshold; Low "watch" for an isolated exceedance.
* Hydraulic: an alert when the model's diagnosis is stable for 5 cycles and changes; at most one per 60 cycles. The recording starts in degraded states, so several fire early. Each alert shows whether the model matched the recorded label (the valve diagnosis is often wrong).
* Energy: usage above the baseline by more than the calibrated threshold for 2 intervals in a row; at most one per 4 hours. This may be legitimate production, not waste.

There is no real kiln data in this project. The earlier kiln dashboard was simulated and has been replaced.

## Real-data result: bearing fault detection

**Data:** NASA IMS `2nd_test` (University of Cincinnati, Center for Intelligent Maintenance Systems). 984 vibration snapshots over about 164 hours, ending in an outer-race failure of bearing 1.

**Method** ([`mlmodel/ims_pipeline.py`](mlmodel/ims_pipeline.py)):
1. Extract 8 features per snapshot: RMS, peak, kurtosis, skewness, crest factor, and three frequency-band energies.
2. Train a PCA reconstruction-error anomaly detector on the **healthy first 25%** of the run only (time-based split, never random).
3. Threshold = mean + 6 standard deviations of the training error. An alarm needs 3 flagged snapshots in a row.

**Result on the live-demo run (2nd_test, bearing 1):**
- 0 false alarms on 246 held-out healthy snapshots
- First sustained alarm about **74 hours before the end of the run**

**Wider check: all 3 NASA tests, 12 bearing runs** ([`mlmodel/ims_multi_eval.py`](mlmodel/ims_multi_eval.py)). One independent model per bearing, each trained on that bearing's own first 25%:

| Test | Bearing (documented outcome) | Result |
|---|---|---|
| 1st | b3 (inner race failure) | Detected, ~253 h before end of run |
| 1st | b4 (roller element failure) | Detected, ~120 h before end |
| 2nd | b1 (outer race failure) | Detected, ~74 h before end |
| 3rd | b3 (outer race failure) | **Missed**: score rose ~9x but stayed under the threshold |

- **3 of 4 failures detected**, with 74 to 253 hours of warning.
- **1 of 4 missed** (3rd test, bearing 3).
- **Before drift, the false-alarm rate was at most 0.4%** in the held-out first half, for all 12 runs.
- **Control bearings** (no reported failure): 5 of 8 raised sustained alarms later in their runs. These are not labelled, so they could be real wear, vibration travelling through the shared shaft, or false alarms. The detector says "something drifted", not which bearing.

**Threshold study** ([`mlmodel/ims_threshold_study.py`](mlmodel/ims_threshold_study.py)): 7 sigma multipliers x 3 "in a row" settings, plus a leave-one-test-out check where the setting is chosen on two tests and scored on the third.
- **The miss is a trade-off, not a bug.** The missed failure (3rd test, bearing 3) is caught at lower thresholds (k=2 to 4), but only after allowing more false alarms: k=4, 3-in-a-row detects all 4 failures with 0.17% first-half false alarms, yet gives that bearing only about 9 h of warning (k=3 gives about 181 h but 0.66% overall alarms).
- **Settings do not transfer between tests.** Leave-one-test-out detected 3 of 4 failures, the same as the fixed default. A setting chosen on tests 1 and 2 gave 2.9% first-half false alarms on the held-out 1st test, and the setting chosen for the 3rd test (k=10) missed its failure.
- **Conclusion:** one global threshold is not enough. Each machine needs its own calibration against a long healthy baseline before alerts can be trusted.

**Per-machine calibration** ([`mlmodel/ims_calibration_study.py`](mlmodel/ims_calibration_study.py)): each bearing's own healthy baseline is split into a fit part and a calibration part, and the threshold is a percentile of the calibration errors times a safety margin (27 settings; no failure labels used). Checked with leave-one-test-out.
- **False alarms became safer to transfer.** In every leave-one-test-out fold the chosen setting gave 0% false alarms in the healthy reference region (snapshots 40-50% of each run). The earlier method's chosen setting gave 2.9% on one held-out test.
- **Detection did not improve under the honest test.** Leave-one-test-out still detected **3 of 4** failures; the subtle 3rd-test failure was missed again because the setting picked on the other two tests was the most conservative one.
- **Some settings do catch all 4** (for example 25% baseline, 99th percentile, 1.5x margin: 4 of 4, about 144 h median warning, at most 0.9% healthy-region false alarms). I found those by looking at all the results, so they are optimistic and not evidence yet.
- With only 4 failed bearings, a difference of one detection is not statistically meaningful.

**Limits (please read):**
- Three test rigs from one lab; same bearing model, speed and load. Not evidence for other machines or plants.
- No labelled fault onset, so lead time is measured against the end of the run.
- Default threshold (mean + 6 sigma, 3 in a row) was fixed once on training data. The study above shows it is a trade-off and does not transfer between tests.
- The live demo is a replay of recorded data, not a live plant.

See [MODEL_CARD.md](MODEL_CARD.md) for details.

## More real machines

### Hydraulic test rig: fault diagnosis ([`mlmodel/hydraulic_pipeline.py`](mlmodel/hydraulic_pipeline.py))
Data: ZeMA hydraulic rig (UCI #447), 2,205 one-minute cycles, 17 sensors, 4 components with labelled condition levels (cooler, valve, pump leakage, accumulator).

- **No usable healthy baseline.** Only **21 of 2,205 cycles** have all four components healthy, so an unsupervised "learn normal, flag drift" detector cannot be evaluated reliably on this dataset. (A first attempt on those 21 cycles gave meaningless numbers, e.g. 4 of 5 held-out healthy cycles flagged, and I did not use it.)
- **So it is framed as diagnosis** (which component is degraded), with a random forest on per-cycle sensor statistics. Neighbouring cycles are near-duplicates, so evaluation never splits a group: by contiguous run, and by whole fault combination (unseen combinations).

| Component | Majority baseline | Accuracy (held-out runs) | Accuracy (unseen combinations) |
|---|---|---|---|
| Cooler | 33.6% | 97.8% | 95.5% |
| Pump leakage | 55.4% | 99.1% | 99.1% |
| Accumulator | 36.6% | 78.9% | 75.7% |
| Valve | 51.0% | 66.6% | 64.3% (balanced 61.2%) |

The valve is poorly diagnosed with simple summary statistics. Labelled faults like this are rare in real plants, so treat these numbers as an upper bound for what labelled data can give.

### Plant energy and CO2 ([`mlmodel/energy_pipeline.py`](mlmodel/energy_pipeline.py))
Data: one steel plant, South Korea, 2018, 15-minute readings (35,040 rows).
- CO2 is **derived from kWh** in this dataset (correlation 0.988, about 0.0004 tCO2/kWh), so it adds no independent signal. `Load_Type` is also derived from kWh and is excluded as a model input.
- An expected-usage model from calendar features only (Jan-Aug train, Sep calibrate, Oct-Dec test) has a held-out mean error of **11.1 kWh vs 28.3 kWh** for a naive average.
- 2.8% of held-out intervals are flagged "unexpectedly high" (6.5% of held-out energy). **There are no waste labels, so this is not validated detection**: unexpected usage can be legitimate production.
- About 55% of active intervals have lagging power factor below 90%, a commonly cited threshold for utility penalties (verify the tariff rules for the actual plant).

### Real plant meters: HIPE ([`mlmodel/hipe_pipeline.py`](mlmodel/hipe_pipeline.py))
Data: **HIPE** (High-resolution Industrial Production Energy), smart-meter readings from a real power-electronics production plant (KIT, Germany, Oct-Dec 2017; CC BY 4.0; [Zenodo 14054775](https://zenodo.org/records/14054775)). Full 3-month set: 10 sub-metered machines plus the plant main meter, 5-second readings (about 15 million rows) aggregated to 15-minute means (8,832 intervals). Please cite the dataset paper: [doi:10.1145/3208903.3210278](https://doi.org/10.1145/3208903.3210278).
- **Splits by date:** profile Oct 1 - Nov 25 (8 weeks), threshold calibration Nov 26 - Dec 9, held-out test Dec 10 - Dec 31 (includes Christmas and New Year).
- **Baseline:** four causal candidates were compared: a median profile per (weekday, 15-min slot) from Oct-Nov, "same time last week", the mean of the last two weeks, and a blend. The winner is chosen **on the calibration weeks only**: *mean of the last two weeks* (calibration MAE 2.26 kW vs 2.36 for the profile). On normal held-out December days: **MAE 2.66 kW** (21.6% MAPE) vs 3.35 for the profile, 2.79 for last week and 6.13 for a naive mean. On Christmas / New Year days (assumed holidays) MAE is 3.21 kW. Flags: 0.6% of normal test intervals, 0% on holidays. *Disclosure:* the candidate list was widened after an earlier run showed "last week" beating the profile on the test weeks; the choice among candidates used only calibration data, but this is not a pre-registered test.
- **Base load is big:** the 10th-percentile plant draw (about 6.3 kW) accounts for **about 45% of all energy**; 78% of intervals have no sub-metered machine running, and 59% of the energy is used in those intervals.
- **Most energy is unmetered:** the 10 sub-metered machines are only **4.1%** of plant energy (VacuumPump1, HighTemperatureOven and ChipPress are the largest). The rest (HVAC, lighting, other equipment) is not visible in this data.
- **Limits:** a single plant and quarter; **no fault or waste labels**, so flags are not validated detections; a simple rolling average beats a learned profile here, so there is little to gain from fancier models on this data; holiday days are an assumption; the "load while machines idle" alert mostly fires around the weekday 07:30 ramp-up and may be legitimate. The replay shows a "data split" tag; the dashboard flags in profile/calibration weeks are in-sample, so plant alerts are only raised in the held-out test weeks (Dec 10-31).
- Results: [`mlmodel/hipe_results.json`](mlmodel/hipe_results.json). Run `python mlmodel/hipe_pipeline.py extract` (needs the 1.3 GB zip at `data/hipe/hipe_full.zip`, gitignored; it is streamed, not unpacked) then `eval`.

## Run it

**Requirements:** Node 18+, Python 3.11 or 3.12 (TensorFlow, listed in the requirements, does not install on 3.14; the bearing demo itself needs only scikit-learn).

```bash
npm install
npm run dev
```

In another terminal, start the backend:

```bash
pip install -r mlmodel/requirements.txt
cd mlmodel
python -m uvicorn app:app --port 8000
```

Open `/home/dashboard`, dismiss the welcome popup, scroll to the **Real Bearing / Hydraulic Rig / Plant Energy** panels and press **Start replay** on each.

To point the app at a different backend, copy `.env.example` to `.env` and set `VITE_KILN_WS_URL`.

### Retrain from the raw data

The raw NASA data (about 1 GB) is not in the repo. Download `IMS.zip` from the [NASA catalog entry](https://catalog.data.gov/dataset/ims-bearings), extract `2nd_test.rar` into `data/ims/2nd_test/`, then:

```bash
python mlmodel/ims_pipeline.py extract
python mlmodel/ims_pipeline.py train
python mlmodel/ims_pipeline.py eval
```
